# structured-output — модель описує, код вирішує

Джерела правди: spec `.claude/specs/script.md`, `src/pipeline/schema.py`; CLAUDE.md №1, №5, №6.

## Принципи

1. **Схема — з pydantic**: `ScriptDraft` → `providers/claude.py` (`output_schema()` прибирає
   ключові слова, яких API не приймає, і робить схему строгою) → structured output. Enum
   (`VoiceProfile`, `Delivery`) фізично не дає вигадати голос чи емоцію.
2. **Репліки в схемі моделі нема.** Її пише юзер (CONTEXT Z1: лапки в тексті або `--line`); код
   валідує її в `Brief` до будь-якого виклику і вставляє в `Script` дослівно. Модель повертає
   лише те, чого не вирішить код: персонажа, `delivery`, опис кадру й руху.
3. **Цикл виправлення, не ретрай**: невалідний вихід → текст помилки назад у промпт (`feedback`),
   до `MAX_SCRIPT_FIX_ATTEMPTS`; кожна спроба — окремий платний виклик через `tracer.spend` зі
   своїм ключем. Далі — стоп з людським повідомленням.
4. **Версія**: зміна промпта чи схеми → інкремент `PROMPT_VERSION` у вузлі (він у ключі кешу —
   інакше старий `script.json` підхопиться як свіжий; і в назві звіту евалів).
5. Модель — запис реєстру (`SCRIPT_MODEL`), не хардкод; перед зміною виклику API — скіл `claude-api`.

## Перевірка

- Тести на fake: `Brief` відхиляє `[whispers]` і дужки в репліці без виклику моделі; невалідний
  `ScriptDraft` (чужий `character_id`, не та кількість шотів) → цикл отримує текст помилки;
  `script.json` містить репліку байт-у-байт.
- На живій моделі — скіл `run-eval` (кілька кейсів, за згодою власника), а не «подивився — ок».

Кінець — скіл `wrap-up`.
