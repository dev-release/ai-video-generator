# CLAUDE.md — правила для агента

Повний контекст завдання: @CONTEXT.md — прочитати перед першим рядком коду.
Поточний стан і наступні кроки: @PROGRESS.md — оновлювати після кожного блоку роботи.

## Як працювати з власником

- Власник — фронтенд-AI-розробник, пише коротко й українською. Відповідай українською, просто;
  **пояснюй рішення**: назва технології + чому вона, а не альтернатива.
- **Короткий запит читай через задачу, не буквально**: CONTEXT («Рішення власника» → §3 → §13) і
  PDF завдання (`docs/task/`, поза git; Ч.4 — MVP). Запит
  можна зрозуміти як «нова окрема річ» або як наявний потік — обирай наявний потік.
- «Протестувати етап» (звук, кадр, відео) = прогін **того самого графа** з потрібними моделями
  (fake/реальні — конфігом); результат — відео, як вимагає завдання. Окремі інструменти, сторінки
  чи ендпоінти для одного етапу поза пайплайном — лише за прямою вимогою власника (AI_LOG 2026-09-30).
- Кожен випадок, коли AI (ти) дав хибний результат і це виправили, — одразу запис у `AI_LOG.md`
  (дата, що сталося, причина, яку дірку в специфікації це показало).
- Частину 1 `NOTES.md` (порівняння стеку) **не пиши** — тільки збирай факти й цифри з джерелами.
- Знання між сесіями — **лише в проєкті**: правило — сюди, стан — у `PROGRESS.md`, помилка — в
  `AI_LOG.md`. Локальна пам'ять агента (`~/.claude`) — лише для фактів про конкретну машину.

## Як вносити зміни (будь-яка задача)

1. **До.** Звір запит із CONTEXT («Рішення власника», §3, §13) і PDF, Ч.4; суперечить або
   неоднозначний так, що від відповіді залежить результат, — спитай власника. Прочитай spec і код,
   який змінюєш. Перед видаленням чи перейменуванням знайди всі використання:
   `grep -rn "<ім'я>" src tests evals ui/src .claude README.md` — і дані на диску: старі чекпоїнти й
   артефакти `runs/` мають відкриватись (хоча б для перегляду), а не падати.
2. **Під час.** Spec → тест → код, малими кроками, за скілом задачі (таблиця нижче). **Одне
   правило — одне місце** (CLAUDE.md, spec або скіл); деінде — посилання, не копія: копії
   розходяться з оригіналом (AI_LOG 2026-09-30, застарілі скіли). Падіння нативного коду (SIGABRT,
   exit 134/139, `libc++abi`) — спершу стек: звіт `~/Library/Logs/DiagnosticReports/*.ips` або
   `python -X faulthandler`, потім гіпотези (AI_LOG 2026-10-01, телеметрія onnxruntime).
3. **Після.** Скіл `wrap-up`. Хук Stop не дасть завершити відповідь, якщо код змінено після
   останнього зеленого `make check`.

## Команди

```bash
uv sync                      # залежності
make test                    # pytest (fake-бекенд, без мережі)
make lint                    # ruff check + format --check
make fmt                     # ruff format + fix
make run IDEA="…" LINE="…"   # повний прогін → runs/<run_id>/final.mp4 (LINE2 — другий шот)
make run-fake IDEA="…" LINE="…"  # прогін на fake-провайдерах, $0
make estimate                # preflight: ключі, голоси, оцінка вартості — без витрат
make eval                    # евали по evals/cases: fake + тон — механіка воріт, $0
make eval-speech             # ті самі евали на справжній мові (Kokoro + whisper локально), $0
make check                   # ЄДИНА умова «готово»: лінт, UI, усі тести, eval-speech
make ui                      # веб-UI: FastAPI :8000 + Vite :5173
make ui-types                # типи TS з OpenAPI після зміни api.py/schema.py
```

## Скіли (`.claude/skills/`) — викликати, коли задача збігається

| Задача | Скіл |
|---|---|
| Реалізувати/змінити вузол, граф, CLI | `implement-node` |
| Нова або виправлена специфікація | `write-spec` |
| Кінець **кожного** блоку роботи: звірка з задачею, дифф, `make check`, PROGRESS, звіт | `wrap-up` |
| AI помилився й це виправили | `log-ai-mistake` |
| Хуки, permissions, нові ворота та їх тести | `harness-gate` |
| Модель у реєстрі, новий API-транспорт, ціни | `add-provider` |
| Промпт / JSON-схема / вихід LLM | `structured-output` |
| Ворота дослівності (`voice_check`, `verify`), ASR, `normalize()`, WER | `verbatim-gate` |
| Евали, метрики, порівняння версій | `run-eval` |
| Факти й цифри для Частини 1 | `stack-facts` |
| Веб-UI: `api.py`, `ui/`, контракт API | `ui-dev` |

На старті кожної сесії (і після compact) хук `session-context.sh` дає в контекст блокер,
наступні кроки з `PROGRESS.md` і список заглушок — починати з «В роботі», потім «Далі».

## Заборонено

1. **Змінювати `Shot.line`** після виходу з вузла `script` — ніде, ніяк (ні trim, ні нормалізація, ні теги).
   Емоції/темп — тільки в `delivery`. Нормалізація для WER — лише в копії для порівняння.
2. Комітити ключі, `.env`, артефакти з `runs/` (тека повністю поза git). `.env` читати можна
   (перевірити, які ключі задані), **писати — ні**: ключі вписує власник (deny + `guard-bash.sh`).
   Значення ключів не виводити у відповідях і логах.
3. Підвищувати `MAX_RUN_COST_USD` чи прибирати перевірку стелі.
4. Глушити помилки: `except Exception: pass`, ретраї на 4xx (і 429), `--no-verify`.
   **Платний запит** повторюється лише коли провайдер точно не виконав (5xx, збій з'єднання);
   таймаут після відправки — ніколи (міг списати). Ідемпотентні читання — ще й на таймаутах.
   Задачі fal пишуться на диск і підхоплюються, а не відправляються вдруге (`retry.py`, spec pipeline).
5. Давати моделі вирішувати те, що вирішує код: тривалості, склейка, гучність, WER, резолв голосу, ліміти.
6. Модель не повертає `voice_id` — лише `VoiceProfile` (enum); резолв через `voices.yaml`.
7. `git commit` і `git push` — лише за прямою командою власника, щоразу окремо.
   Зміни лишаються в робочому дереві; у відповіді сказати, що вони не закомічені.

8. Писати код під конкретну модель. Оболонка навколо моделей — одна для всіх: модель описується
   записом у `src/pipeline/models.yaml` (ендпоінт, шаблон аргументів, шлях до результату, ціна з
   джерелом, ключ, таймаут, ліміти) і обирається конфігом (`VIDEO_MODEL=…`). Нова модель на
   наявному транспорті — лише yaml. Новий транспорт — один адаптер на протокол можливості, без
   гілок `if model == …`. Кожна модель у реєстрі проходить ті самі контрактні тести. Spec:
   `.claude/specs/providers.md`.
9. Автоматично витрачати гроші на те, що вже оплачено або що точно впаде: будь-який платний
   виклик іде через `nodes.produce` / `tracer.spend` (ключ до резерву → кеш → повернення резерву),
   ліміти наступних моделей перевіряються ДО платного кроку, фінальні ворота не перегенеровують
   платне автоматично.

## Стиль

- Python 3.12+, pydantic v2 для всіх меж між етапами, type hints скрізь.
- Кросплатформність і **мінімум локального**: проєкт запускає інша людина на іншій машині.
  AI-моделі — лише через API; локально — ffmpeg (pip) і легкі детермінованi інструменти (OpenCV).
  Важкі локальні моделі — тільки опційним extra, ніколи в дефолтному шляху чи тестах. Жодних
  `say`, brew, системного ffmpeg. Нова локальна залежність → живий smoke до того, як на ній будувати.
- Кожен вузол: чиста функція `(state) -> patch`, артефакти на диск під `runs/<run_id>/`, ідемпотентна за хешем входу.
- Логи/трейс — через `obs.py`, не `print`.
- Коментарі й docstrings — **англійською** і лише там, де без них не зрозуміло «чому»; «що» не
  коментується. Вивід CLI, повідомлення помилок і тексти UI — англійською. Документи harness
  (цей файл, specs, skills, PROGRESS, AI_LOG) — українською.

## Що означає «готово» для задачі

- **`make check` зелений** — єдина умова «готово». Він перевіряє те, що бачить людина: приймальні
  тести (кожне медіа, яке показує UI, повне й відтворюване), браузерний тест у справжньому Chrome,
  евал на справжній мові, звірку документів з кодом (`tests/test_docs.py`) і те, що ворота harness
  падають, коли мають (`tests/test_harness.py`). Зелені юніт-тести самі по собі «готово» НЕ
  означають (AI_LOG 2026-09-30: відео 0 с і 0/20 на справжній мові при 198 зелених тестах).
- Процедура — скіл `wrap-up`: звірка з задачею, власний дифф, документи, `make check`, сценарій власника.
- Змінив те, що бачить людина (UI, медіа, повідомлення) → приймальний або браузерний тест на це.
- Заглушки віддають ті самі типи й формати, що реальні провайдери.
- Поведінка відповідає специфікації етапу; нові інваріанти покриті тестами.
- Якщо була помилка AI — є запис в `AI_LOG.md`.
